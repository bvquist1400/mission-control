# Baseline (Mission Control)

> **Maintenance:** Keep this file and `AGENTS.md` in sync. Update both when adding new architectural patterns, key files, migrations, or environment variables. This is a living conventions doc, not a changelog.

Personal productivity and project management platform for tracking implementations, projects, tasks, stakeholders, commitments, and calendar events.

## Stack

- **Framework:** Next.js 16 App Router (Turbopack)
- **Database:** Supabase (PostgreSQL + Auth + RLS)
- **Styling:** Tailwind CSS with custom theme tokens
- **Deployment:** Vercel (two deployments — main app + MCP proxy)
- **MCP:** Model Context Protocol server with OAuth, used by Claude.ai and ChatGPT

## Commands

```bash
npm run dev          # Local dev server
npm run build        # Production build (runs tsc)
npx tsc --noEmit     # Type-check without building
```

## Priority Model

- `tasks.base_priority` is the un-boosted base (0-100); `tasks.priority_score` is always derived as `clamp(base_priority + boosts, 0, 100)` via `recalculateTaskPriority()` in `src/lib/priority.ts`.
- Never feed `priority_score` back in as the base — that recreates the pre-migration-044 compounding bug.
- API `priority_score` inputs (create/PATCH/MCP) set `base_priority`; the stored score is recomputed server-side.

## Data Hierarchy

```
Implementation (Application) -> Project -> Task
```

Hierarchy is DB-enforced (migration 046, project wins): a task in a project inherits the project's `implementation_id` via trigger; re-pointing a project cascades to its tasks. Caller-supplied `implementation_id` is overridden when the project has an application; kept only when the project has none or the task has no project.

External task identities are stored as the nullable pair `external_source_system` + `external_source_id`. Migration 054 enforces user-scoped uniqueness; callers must never assign an external ID without its source-system namespace.

## Architecture Rules

### API Routes

- Auth: use `requireAuthenticatedRoute()` from `@/lib/supabase/route-auth`
- Machine keys (`X-Mission-Control-Key`, all act as `MISSION_CONTROL_USER_ID`): legacy `MISSION_CONTROL_API_KEY` reaches every route; `MISSION_CONTROL_ACTIONS_API_KEY` only its allowlist, no DELETE; `MISSION_CONTROL_FAMCAL_API_KEY` (authSource `famcal_api_key`, `src/lib/famcal-api-key.ts`) only personal tasks for the FamCal Sunday brief: `GET /api/tasks` (forced `tag=personal`; a strict allowlist of query parameters, `FAMCAL_LIST_PARAMS` = tag, limit, offset, status, owner, needs_review, due_soon, include_done, include_parked, include_missed; anything else, e.g. `view`, the work-relation or external-source filters or `scope`, and any parameter given twice, is a 400 even when empty; dependency rows aligned with the task detail: a prerequisite task the key may read by id keeps its id/title/status, taken from one eligibility-filtered read; any other task and every commitment is redacted, `redactDependencyForFamcalList`), `GET|PATCH /api/tasks/{uuid}`, `GET|POST /api/tasks/{uuid}/comments`, `POST /api/tasks/park/{uuid}`. Eligibility (Brent 10/16, "Leave it out of the brief"; one SQL definition, `famcal_eligible(tasks)` in migration 060, a PostgREST computed field): the task's own tags contain `personal`, it has no sprint, and EITHER it has no project, no application and no section (a standalone to-do) OR its project is the same user's and is itself tagged `personal`. Every FamCal read and write filters on `famcal_eligible = true` in the same query (list, detail, the PATCH/park guard and UPDATE, comment GET) or under the comment function's row locks, so the list pages over eligible tasks only and an ineligible task is the same 404 as a missing one. Every task it gets back (list, detail, PATCH, park) goes through `projectTaskForFamcal()`: the task's own `FAMCAL_TASK_FIELDS` only (no `source_url`); `recurrence` rebuilt from `FAMCAL_RECURRENCE_FIELDS` (scalar scheduling fields, never `template_task_id`); application and sprint always null. Personal-project rule: the project (id/name/stage/rag/tags) and its section are returned only when the project itself carries `personal`; a personal task in any other project gets project, project_id, section_id and section_name null. So a personal task filed under work never shows work names, ids or metadata. PATCH takes only `status` (Done/Parked, or reopen from Done/Parked), `due_at`, `follow_up_at` (a date, never cleared); its UPDATE carries `contains(tags, [personal])`, `famcal_eligible = true` and, for a status change, `status = <the status the transition was checked against>` (a concurrent change → 409, a lost tag → 404); park's read and UPDATE carry the tag and eligibility. Comment POST is one RPC, `famcal_add_personal_task_comment` (migration 060: its first locking read already filters on `famcal_eligible(t)`, so an ineligible task is never waited on and a busy work task answers like a missing id; then it locks the task FOR SHARE and, when it has one, its project FOR SHARE, re-checks user + eligibility under those locks and inserts, one transaction, so a task or project re-tag either waits or is seen; waits are capped by the function's 5s `lock_timeout`, and a timeout (55P03/57014, only possible on an eligible task) is a 503 "busy"; no rows → 404; a SQL error rolls back, but a reply lost after commit is ambiguous and there is no idempotency token, so callers must not auto-retry); comment GET is one query (the task filtered by user + tag + eligibility with its comments embedded). A FamCal value equal to the legacy or actions value fails closed: `src/lib/machine-keys.ts` refuses that value for every caller (route-auth, legacy `/api/mcp`, `generate-recurring`) with 401 and logs the env var names. Not uniform by design: CORS preflight `OPTIONS` is answered by `src/proxy.ts` before auth (no data), and `/api/mcp`, `/api/mcp-upstream` and `generate-recurring` authenticate themselves (an unknown key there is 401, not 403). A route that adds a per-task read or write and joins that allowlist must add the same guard and projection. `npm run test:famcal-api-key` pins all three keys; `test:famcal-db` (local stack) checks 060, the lock under overlapping transactions and the routes on a real database.
- CORS: wrap all responses with `withCorsHeaders()` from `@/lib/cors`
- PATCH: always use an explicit `allowedFields` allowlist
- Not-found checks: only translate PGRST116 into 404 (use `isPostgrestNotFound()` from `@/lib/supabase/errors`); rethrow other errors as 500s
- Timestamp inputs: validate with `validateOptionalTimestamp()` from `@/lib/validate` before insert/update
- Secret/API-key comparisons: use `secureCompare()` from `@/lib/secure-compare`, never `===`
- Supabase queries: always filter by `user_id`
- Email intake `POST /api/intake/email` (header `x-api-key` = `N8N_INTAKE_API_KEY`, acts as `DEFAULT_USER_ID`; a session also works): without `mode` it stores an `inbox_items` row, runs the AI extraction and creates a Backlog task (the n8n behaviour). `mode: "inbox_only"` stores the row with the excerpt (at most 2,000 characters, NUL and lone surrogates cleaned) in `llm_extraction_json` as `{ intake_mode: "inbox_only", body_snippet, body_snippet_truncated }` and stops: 201, no model call, no task, `triage_state` stays New. Any other `mode` is a 400, checked before the required fields so `{ mode: "<unknown>" }` alone is a side-effect-free version check (the support-mail Apps Script uses it); a repeat `message_id` is 200 in both modes. MCP `fetch` of `email:<id>` shows that excerpt as plain text. `npm run test:intake-email` (offline) pins both modes.

### Database

- RLS: 4-policy pattern (SELECT, INSERT, UPDATE, DELETE) on every table
- `updated_at` triggers: reuse `set_updated_at()` function
- Migrations: `supabase/migrations/` (latest: 065); rollbacks in `supabase/rollbacks/`
- New tables get explicit `GRANT ... TO authenticated, service_role` (see 055): newer Supabase stacks, including a fresh `supabase start`, no longer auto-grant public tables to the API roles

### Schema Types

- `src/types/supabase.generated.ts` is generated truth — never edit by hand. Regenerate after every migration: `npm run gen:types`; verify with `npm run test:types-drift`.
- `src/types/database.ts` remains the domain layer (narrowed unions like `TaskStatus`); `src/types/type-assertions.ts` compile-time-pins its row interfaces to the generated schema (key parity + nullability), so `npx tsc --noEmit` fails on drift.
- Supabase clients are typed with `<Database>` — inserts/updates are schema- and enum-checked at compile time. JSONB domain shapes (e.g. `TaskRecurrence`) cast via `as unknown as Json` at the write boundary.

### MCP Server

- Stateless per-request transports with `enableJsonResponse: true`
- Tools call the HTTP API internally via fetch
- Responses wrapped with `toMcpResponse()` which adds `current_time_et`
- Tool surface is a live contract: `npm run test:mcp-contract` diffs tool names + input schemas against `scripts/fixtures/mcp-tools.snapshot.json`; rerun with `--update` and commit when a change is intentional
- Proxy deployment (`DEPLOYMENT_ROLE=mcp`) at `mission-control-mcp.vercel.app`
- Proxy must: strip `content-encoding`/`transfer-encoding`/`content-length` from upstream headers, add CORS headers explicitly, use `sessionIdGenerator` (clients require `mcp-session-id`)
- OAuth: RFC 8414/9728 flow with PKCE, dynamic client registration, token rotation
- OAuth redirects must use status 302 (not Next.js default 307)

### UI Conventions

**Use the UI primitives — do not hand-style controls.**

| Need | Use |
|---|---|
| Button | `<Button variant="primary\|secondary\|danger\|success\|ghost" size="icon\|xs\|sm\|md\|lg">` (`@/components/ui/Button`) |
| Segmented control / tab strip | `<Button variant="toggle" active={isSelected}>` — sets `aria-pressed` for you |
| Icon-only button | `<Button variant="ghost" size="icon" aria-label="…">` |
| Button-styled `<Link>`/anchor | `buttonClasses({ variant, size })` |
| Text field / textarea / select | `<Input>` / `<Textarea>` / `<Select>` with `tone="default\|muted"`, `size="xs\|sm\|md"` (`@/components/ui/Field`) |
| Card surface | `className={cardClasses({ padding: "sm\|md\|lg" })}`, or `<Card as="section">` (`@/components/ui/Card`) |
| Pill / badge | `className={badgeClasses({ tone, size })}`, or `<Badge>` (`@/components/ui/Badge`) |
| Transient feedback | `useToast()` (`@/components/ui/Toast`) — never `window.confirm`/`alert` |
| Task mutation | `useTaskMutation()` (`@/hooks/useTaskMutation`) — owns optimism, rollback, undo |

Controls with behaviour (Button, Input) are components; pure-styling primitives (Card, Badge) expose class functions so the semantic element stays the author's choice.

- A primitive's `className` prop is for **layout only** (margin, width, flex/grid placement). Every colour, padding, radius and font size is a `variant`/`size`/`tone` prop — there is no `tailwind-merge`, so a conflicting utility passed via `className` will not reliably win. Add a variant instead.
- Theme tokens: `text-foreground`, `text-muted-foreground`, `bg-panel`, `bg-panel-muted`, `border-stroke`, `rounded-card`, `bg-accent`
- Semantic tokens: `danger`, `warning`, `success` — each with `text-*`, `bg-*-soft`, `border-*-border` (danger also has `bg-danger-soft-hover`). Never reach for raw Tailwind palette shades (`bg-red-50`, `text-slate-700`, `bg-amber-50`): the app is dark-only, and those render as pale light-mode boxes. For accents on dark, the `bg-*-500/15` + `text-*-300` pattern is fine.
- `bg-accent` is a **fill-only** token: white on it is 5.84:1, but as text it is 2.96:1 on `bg-panel`. For accent-coloured type, icons or rings use **`text-accent-text`** (6.2:1).
- Focus: a global unlayered `:focus-visible` outline lives in `globals.css`. Do not add `outline-none` without a visible replacement, and do not add `focus:ring-*` — the outline covers it.
- Type floor: `text-xs` is the smallest size in the app. Do not reintroduce `text-[10px]`/`text-[11px]`.
- Page headers: `<PageHeader title="..." description="..." actions={...} />`
- Detail pages: server component wraps params, passes id to client component

### Navigation & shortcuts

- Nav lives in **one** place: `src/components/layout/nav-items.tsx` (`NAV_GROUPS`). The desktop rail, mobile drawer and tablet bar all render from it — never add a link to only one of them.
- Adding a route means adding it to `NAV_GROUPS`, or deliberately leaving it unlinked (`/triage` and `/implementations` are intentional redirect shims).
- Sidebar collapse state is a **cookie** (`baseline_sidebar`), read in `src/app/layout.tsx` so the rail renders at its final width server-side. Don't move it to localStorage — that reintroduces the expand-then-collapse flash.
- Global shortcuts live in `Sidebar.tsx`: `⌘/Ctrl+K` search, `[` collapse, `?` help, `g` + key to navigate (`GO_TO_KEYS` in `ShortcutsDialog.tsx`). Any new shortcut must be added to the `?` dialog in the same change, and must no-op while the user is typing in a field.

### Brief pages

- A brief (`briefs`, migration 055) is content-as-data plus numbered items (`brief_items`) with a stable `item_key` and a state. Editions are `eod` (`EOD-0924`, weekdays 4:15 PM ET, `docs/routines/eod.md`) and `am` (`AM-0928`, weekdays 8:00 AM ET, `docs/routines/morning.md`); `BRIEF_EDITIONS` in `src/lib/briefs/types.ts`.
- `src/lib/briefs/service.ts` is the only write path: `/api/briefs` (POST save, GET `?latest=<edition>`, GET/PATCH by code) and the MCP tools `save_brief(edition)` (with `save_eod_brief` kept as its EOD alias), `get_brief` (by `code` or `latest`), `act_on_brief_items` all go through it. Validate every action before executing any. Every item state change goes through the `brief_item_transition` RPC (055): a row-locked compare-and-set on the validated state, with Accept's task insert and every carry action's task writes in the same transaction (no claim-then-write). A caller that lost a race gets `conflict: true` (HTTP 409), never success.
- Proposals are never tasks until accepted. Accept creates the task with external source (`eod_proposal`, `item_key`), idempotent via the 054 index. A same-day re-save only appends items from uncovered meetings; existing `n` and state never change.
- Meeting coverage hands off EOD → AM: the EOD marks a meeting covered only once it has ended and has notes; the next AM brief reads Granola meetings since the last EOD's date that aren't in its `covered_meeting_ids` and proposes their items (prompt-only, `docs/routines/morning.md` step 5). Proposal keys are meeting + note lines, never the date, so a late item can't be proposed twice.
- Comments hand off the same way: the briefing digest's activity window (`since`) starts at the previous brief's first save, either edition (30 minutes early, since a routine reads before it saves), skipping a same-day rerun's own brief, never more than 4 days before the ET day start (`COMMENT_WINDOW_MAX_DAYS`), else the day start; an explicit `since` overrides, still capped. Comments are fetched for that window, not the calendar day, so an evening or weekend comment reaches the next brief. The digest's `new_comments` lists every work task commented on in the window (id, title, status, owner, count, latest author via `commentAuthor()`, gist via `commentGist()`, hand_back/review/handoff `flags`; hand-backs first; personal tasks dropped; top 20 with real totals); `recent_update` on listed tasks is unchanged. Pure rules in `src/lib/briefing/comment-window.ts`, previous-brief read `listRecentBriefSaves()` in the briefs service (a read failure falls back to the day start). Both routines read full threads with `list_task_comments` (read-only; they still never comment) and show hand-backs, HANDOFF and REVIEW comments in a "New comments" tile.
- Work digest (Baseline task edb01f58, no migration): Brent's Copilot writes a de-identified mail/Teams digest twice a day and his work PC files it as a working note titled exactly `Work digest YYYY-MM-DD AM` / `PM` (layout: `work-digest` skill section 4; the filer adds a last "Filed from the Cooper digest file on …" line, which is privacy-scanned like the body and kept only as a strict ET date-time rebuilt from its numbers, `parseFiledAt`, else `filed_at` null). `get_brief_digest` returns `work_digest` (`{ date, am }` for morning/midday, `{ date, am, pm }` for eod; each `ok` with `note_id`, `window`, `filed_at`, `items[]` W blocks, `still_waiting[]` S blocks and the two counts, or `missing`, or `unreadable` + `reason`; eod's `am.in_morning_brief` says whether today's AM brief recorded the note). Parser and read are pure in `src/lib/briefing/work-digest.ts` and re-validate everything on read, because a note can be hand-edited: counts bounded (20 W, 10 S, equal to the header), unknown keys/sections and stray lines dropped, strings capped, the filer's privacy scan repeated; the older layout (no `status`, no S blocks) is unreadable; a failed read never throws. A `proposed_task` may cite `source.work_digest: { note_id, edition, blocks: ["W3"], lines: [<what line>] }` instead of (or as well as) meetings; save re-reads the note and refuses (400) a citation whose lines aren't those blocks' `what` lines, a note of another day than the brief (the AM brief cites today's AM note, the EOD today's AM or PM) and a note the reader calls unreadable (same `checkWorkDigestBody`: body date/edition must match the title), rebuilding `lines`, `date`, `where` from the note and dropping `detail`. Keys of a digest-citing proposal hash only the cited `what` lines, never the note id or any meeting it also cites (am/pm windows overlap and a meeting may corroborate, so the same quote is one item; meeting-only keys are byte-identical to before). `content.work_digest_note_ids` records the notes a brief read (also every cited one); a same-day rerun appends digest items only from notes not recorded there (`work_digest_already_covered`). Accept: description only "From <code> #n:" + "Work digest <date> AM, W3 (Mail)" + the line (plus any meeting citations; never `detail`), tag `from-work-digest`, `source_type` "Work digest" (free text, no enum) and `source_url` `/r/note/<id>` when no meeting is cited (`proposalTaskSource`). Page: a "Mail · Work digest AM" chip, the quoted line linking the note, and the section heading follows the sources (`proposalSectionTitle`); the hero counts digest-only proposals as "from mail and Teams" (`counts.from_mail`, absent when 0; `countBriefItems` in `src/lib/briefs/counts.ts`). Brief copy never names the AI product: the page and Telegram fallback line is `assistantReviewLine` ("Or ask your AI assistant: review <code>", `src/lib/briefs/copy.ts`). The "From mail and Teams" tile, waits and the 3-proposal cap are prompt rules (`docs/routines/*.md`). Tests: `npm run test:work-digest` (offline; fixtures `scripts/fixtures/work-digest/`).
- "Tomorrow" is the next ET weekday (`resolveTomorrowDate` in `src/lib/briefs/keys.ts`), never UTC.
- The page renders from registries, never from the edition: `CARD_REGISTRY` (item kind → card, `src/components/briefs/cards.tsx`) and `TILE_REGISTRY` (read-only tile type → tile, `tiles.tsx`). Adding a kind means the registry plus the migration's kind check.
- Morning-vs-evening differences come from data only: a meeting that hasn't ended by the brief's save and has no notes yet is "upcoming" (solid block, `prep` line, `task_ids`; an 8:00 meeting under way at an 8:03 save counts; free bands for the rest of the 8:00–4:30 window; `src/components/briefs/timeline.ts`), the notice quotes a "done" stat if there is one, else the first stat, and a tile's `href` may link another brief (only `/briefs/<CODE>` survives validation, `src/lib/briefs/href.ts`). Never branch on the edition.
- `/briefs/*` renders full-bleed (no sidebar) via `AppShell`; its styles are scoped under `.brief-page` and follow the OS light/dark setting, unlike the rest of the app. Page-local keys (J/K/A/D/S) are listed on the page, not in the global `?` dialog.
- Delivery: the first save of a brief claims `notified_at` (UPDATE … WHERE notified_at IS NULL) and sends one Telegram message (`src/lib/briefs/notify.ts`); `notify_sent_at` is written only after delivery; reruns never resend and report `already_claimed`, and a missing env var or failed send records `notify_error` instead of failing the save. Routines never email or message.
- The app shell shows today's (ET) brief as a button (`BriefReadyButton`, desktop rail + phone/tablet top chrome): the brief created last today (the AM brief until the EOD saves), lit with open items, a quiet "· done" once everything is decided, nothing without a brief. The layout renders it; it re-reads `/api/briefs/today` on navigation.
- Pick a date (migration 064, Baseline task 57224ad9): Accept's `due` may be any real `YYYY-MM-DD` from today (ET) to 2 years ahead (it no longer has to equal `suggested_due`; the floor is today, not the brief's date, so an old brief can't land a task on a day that has passed); carry items take `move` with `date` (same rule: `pickedDateProblem(date, now)` / `resolvePickedDueAt(date, now)` in `src/lib/briefs/due.ts`, due = end of that ET day, DST-correct; a past or impossible date is a 400 and nothing runs). Move writes exactly what Tomorrow writes (due_at + recomputed priority through `brief_item_transition`, item `deferred`); the brief's write path has never run the date cascade, so neither does Move. Undo on a deferred carry item (Tomorrow or Move): 064 adds `brief_items.prior_due` (JSONB `[{id, due_at, applied_due_at}]`), written by `brief_item_transition` in the same transaction that moves the tasks and cleared when the item reopens; Undo sends each task's `due_at` back (null = none) with `expect_due_at`, and the function refuses the whole undo (SQLSTATE `MC064`) if a task's date is no longer the one the move set. Items deferred before 064 have no snapshot, so no Undo (`can_undo` false; the API strips `prior_due` and returns only `can_undo`). Repeating a move or Tomorrow that leaves the same day is a no-op; Tomorrow or Move to a different day than the item already went to is refused (Undo first), so "already" never hides a task sitting on another date. A refused Undo (MC064 / no snapshot) comes back with `undo_blocked` and the page drops the dead Undo link. Parked/Done get no Undo. MCP `act_on_brief_items` has `move` + `date`, and `due`/`undo` as above. Tests: `npm run test:briefs-pick-date` (pure, with an in-memory stand-in for the RPC) and `test:briefs-pick-date-db` (local stack: 064 apply/rollback/re-apply, snapshot, Undo, MC064).
- Tests: `npm run test:briefs` and `test:briefs-am` (pure; `test:briefs-am` also pins the comment window), `test:briefs-db`, `test:briefs-review-db`, `test:briefs-r2-db` and `test:briefs-am-db` (need a local Supabase stack; refuse non-local URLs).
- Loading: `src/app/briefs/[code]/loading.tsx` shows the page frame at once while the brief is read. `getBrief` reads the brief with its items embedded (`brief_items(...)`, filtered by `brief_items.user_id`, ordered by `n`), then the tasks: two reads in a row, not three; `getTodayBriefStatus` (root layout, every page) embeds the item states in one read. `npm run test:backlog-speed` pins both.

### Backlog loading (speed check fix 1, Baseline task 7b92254a)

- `BacklogList` loads tasks through `src/lib/backlog/task-loader.ts` (pure): pages of 200 from `GET /api/tasks`, four requests at a time (`fetchAllBacklogTaskPages`); Missed tasks only when the Status filter is Missed (`include_missed=true` while it is on; switching to it fetches `status=Missed` and merges them, `withMissedRows`). No timer: the list refreshes when the tab becomes visible or the window regains focus (`attachRefreshOnReturn`), never while hidden, never while another load runs and not within 2 s of the last (`createRefreshGate`); a refresh that started before a local edit is dropped, and unchanged data keeps the same arrays (`reuseUnchangedRows`) so the table doesn't redraw. TaskGrid takes the parent's `sprints` (one `/api/sprints` read).
- Tests: `npm run test:backlog-speed` (offline: the loader rules, the gate with a fake page, BacklogList wiring, call counts through the real `/api/tasks` handler against the base loop, the brief reads).

### Task owner and the Portfolio page

- Every task has an `owner` (migration 056): `'brent'` means Brent must act, `'agent'` (the default) means an agent holds it; `owner_label` names the agent ("PM", "Codex"); `status_line` is one plain sentence on where it stands. `parseTaskOwnerFields()` (`src/lib/task-owner.ts`) validates all three for POST/PATCH `/api/tasks` and mirrors the DB checks (owner label ≤ 40, status line ≤ 280, whitespace collapsed, empty clears). MCP `create_task` / `update_task` take them; `list_tasks` filters by `owner`. A bulk insert where only some rows set `owner` sends NULL for the rest (PostgREST), so set it on every row or on none.
- `/portfolio` (`src/app/portfolio/page.tsx`) is built in code by `buildPortfolio()` (`src/lib/portfolio.ts`, pure, tested) from `loadPortfolioInput()` (`src/lib/portfolio-queries.ts`, paged task reads): one row per application with % done (task credit ÷ all tasks, recurring templates excluded; a Done task is 1, any other task is its ticked ÷ total checklist items, 0 with no checklist: `taskCredit()`, items loaded in one paged read by `loadChecklistProgress()`; the section timeline fill and Behind/Ahead use the same credit, the "done" counts stay whole tasks, and 100% still needs every task Done), the newest open `status_line` (else the app's summary), next, and owner counts; a `<details>` timeline of project sections from task created/due dates in ET (dashed when no due date, 12 weeks ahead at most). Scope `?scope=personal|work|all`, default personal.
- `/portfolio` and `/r/*` render full-bleed like `/briefs/*` and reuse the brief-page v5 styles (wrapper `brief-page pf`); new classes are prefixed `pf-` because generic brief-page classes (`.prog`, `.open`, …) would otherwise apply.
- Record pages (`/r/[kind]/[id]`) render Markdown with `<Markdown>` (`src/components/markdown/`, parser `src/lib/markdown.ts`): no raw HTML, links limited to http(s)/mailto/same-site. ### Cascade due dates (S1: engine, API, MCP, FamCal)

- When `PATCH /api/tasks/[id]` moves `due_at` LATER, the tasks that wait on it (active task→task links) move too. Plan in TypeScript (`src/lib/task-date-cascade.ts`, pure planner + paged graph read), apply in ONE Postgres function (`apply_task_date_cascade`, migration 061). Brent's rules (comment cae08d4f): mode chosen each time, `cascade_mode` `same_gap` (default: same number of Mon–Fri working days on the ET date, each task keeps its ET time of day) or `only_collisions` (only a task that would now be due before a task it waits on moves, to that ET day; nothing already out of order is "fixed"); `cascade: false` = just this task; `cascade: "preview"` = plan only, nothing written (200 `{ preview: true, cascade }`). Earlier moves, cleared dates, same-day moves, Done or recurring roots never cascade; a first due date cascades only in `only_collisions`.
- Walk: each task visited once (cycles and diamonds end), depth ≤ 20, ≤ 500 tasks reached (more → 409 `too_large`, even with confirm). Done stops the walk; Missed and recurring (template or instance) never move and stop it; Parked and undated tasks never move but are walked through. Floor: a moved task never ends before a task it waits on that moved in this cascade. Only `due_at` moves (never `follow_up_at`), and the project's target date never moves. More than 25 moves → 409 `needs_confirm` with the preview, nothing saved; resend with `cascade_confirm: true`. TaskGrid's bulk "set due date" sends `cascade: false`.
- The root's own UPDATE is a compare-and-set on the due date the plan was made from whenever moves are pending: if another edit moved it meanwhile, the PATCH is a 409 and nothing is saved (two overlapping edits can't stack their gaps).
- The function (061): per-user advisory lock (shared with the loop guard), root re-check (the root must still have the date just saved and not be Done or recurring, else `superseded`, nothing moves), locks targets in id order and then the root's and targets' projects FOR SHARE (060's order) before reading eligibility, compare-and-set per task on the planned old date + open status + not recurring (a task changed meanwhile is skipped as `changed`, never overwritten), one `source='system'` comment per moved task, new `priority_score` (computed in TS; the current score is kept when `base_priority` changed since planning), log rows in `task_date_cascades` / `task_date_cascade_moves` (old/new due and priority, comment id, `undone_at` for S2's Undo), and project flags: a moved task past its project's `target_date` (ET date) turns RAG Green → Yellow (Yellow/Red untouched, `status_summary` never written), adds a system comment on the root and a `project_flags` entry. `lock_timeout` 5s. SECURITY INVOKER; callable by `authenticated` (own id only) and `service_role`; 061 also grants `famcal_eligible(tasks)` to `authenticated` because the function calls it under the app session.
- Reply: non-FamCal PATCHes that include `due_at` get a `cascade` object: `status` (`moved`, `nothing_to_move`, `off`, `not_applicable`, `superseded`, `failed`, `preview`, `needs_confirm`, `too_large`), `mode`, `delta_workdays`, `reason`, `cascade_id`, `message`, `moves[]` (task_id, title, old_due_at, new_due_at), `skipped[]` (task_id, title, reason), `project_flags[]`, `depth_limited`. The known two-statement seam: the root's UPDATE and the function are separate statements; if the function fails after the root saved, the PATCH is still 200 with `cascade.status: "failed"` and a system comment on the root says the later tasks were not moved. A graph read that can't be proven complete is a 503 before anything is saved.
- FamCal key: always the default same-gap cascade (it can't send the new keys; its allowlist refuses them), scope `famcal`: the link read itself is filtered on the WAITING task's personal tag + `famcal_eligible` (inner join `waiting:tasks!task_dependencies_blocked_task_id_fkey!inner`), so a task it can't see is never paged, counted toward the limits, read with its fields or moved, and ends the walk; the function re-checks eligibility under the row and project locks and never waits on an ineligible row. Its reply stays exactly `projectTaskForFamcal` (no `cascade` key). Over 25 moves, too large, unreadable links or a failed apply: only its own task moves and a plain system comment on that task says so (written through `famcal_add_personal_task_comment`). Reverse leak: on a FamCal-visible moved task the comment is the redacted one ("Due date moved from X to Y because a task it depends on moved later.": no title, date or gap of the other task) unless the edited task was FamCal-visible when planned and under the function's locks and still has the title the named text carries (so a rename + re-tag in the same PATCH can't publish the old title); a FamCal-visible root gets no comment at all about a work project past its target.
- MCP `update_task` takes `cascade`, `cascade_mode`, `cascade_confirm`; its description says how to opt out. Undo, switching and the UI are S2 (below).

### Multi-day tasks (S1: start date + rules; migration 063)

- Brent 10/26: "i should be able to manually modify a task and have a start and end date". `tasks.start_at` (migration 063, nullable, no backfill) is the optional START; `due_at` stays the END. In the task window (`TaskMetaEditor`) "Start" sits next to "Due": same input and shortcuts, saved at the start of the local day (`resolveStartDateInput` in `src/components/utils/dates.ts`; due stays end of day), and a start after the due shows "The start date can't be after the due date." with Save disabled when the edit changes either date; a start already saved after the due (an Undo or a FamCal due move) shows a repair hint instead and doesn't block an edit that leaves both dates alone (fix round 1, F4). `POST`/`PATCH /api/tasks` and MCP `create_task` / `update_task` take `start_at` (ISO; null or "" clears); every task read that selects `*` returns it.
- Rule start ≤ due: the API refuses (400, `START_AFTER_DUE_ERROR`) any POST/PATCH that would leave the start after the due date, including a PATCH that moves only the due date before the start. 063 backs it with a TRIGGER, not a CHECK (`trg_tasks_guard_start_at`, errcode 23514, mapped to the same 400 by `isStartAfterDueViolation`): it refuses only writes that set or change `start_at` (INSERT, `UPDATE OF start_at` with a new value), so the cascade functions (061/062), which write only `due_at`, never fail on it, including an Undo that puts a due date back before a start set since. The FamCal key can't send `start_at` (allowlist), its task view leaves it out, and its due-date moves are not checked against the start (it can't see or fix it). A start left after the due by such a due-only write reads as a one-day task on the due date. Concurrent edits (fix round 1, F1): an ordinary PATCH compare-and-sets the date it doesn't write, as it read it (`expectedOtherDate` in `task-range.ts`: a due-only move keys on `start_at`, a start-only move on `due_at`, null-aware; a PATCH with both dates writes the pair it checked), so a start and a due written by two clients at once can't both pass; the loser gets 409 `TASK_DATES_CHANGED_ERROR` and nothing is saved. The FamCal key and the cascade functions (apply, Undo, switch) are exempt.
- Cascade unchanged: it moves only `due_at` (later), so a push lengthens the range; `start_at` never moves (no change to 061/062 SQL).
- Rules are pure in `src/lib/task-range.ts` (`npm run test:task-range`): `isPastDue` / `isTaskLate` (late only once the due instant has passed; Done/Missed/Parked never late; a start date never makes a task late), used by the briefing snapshot's overdue list and count, the digest's "Overdue since" label, the weekly review's stalled check and the intelligence detectors; `rangeOf` / `dayOfRange` ("Day X of Y" on ET dates: work tasks count Mon–Fri, personal tasks (`personal` on the task or its project, `isPersonalTaskOrProject`) count every day; a Sat→Sun work range counts its days); `checklistProgress` (ticked ÷ all rows; weighted by row `unit_count` when any row has units, a row without units weighing the average; else equal); `isBehindPace` (days gone share − progress share ≥ `BEHIND_PACE_GAP` 0.2; days gone = counted days before today); `taskRangeState` (one call per card: kind none/closed/late/due_today/in_range/before_start/upcoming, day, elapsed, progress, behindPace, allStepsDone) and `rangeChipText`. The card fill UI is S2 (below).
- Deploy order: 063 before the app (the app selects and writes `start_at`); rolling 063 back needs the app rolled back first (`supabase/rollbacks/063_add_task_start_at.down.sql`; start dates are lost). Tests: `test:task-range` (offline) and `test:task-range-db` (local stack + `RANGE_TEST_*`: 063 rollback/re-apply, the trigger, the real routes, the cascade and its Undo leaving `start_at` alone).
